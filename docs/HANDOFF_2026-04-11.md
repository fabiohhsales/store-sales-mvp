### 3.1 Wave 1 — `5492fe1` (21:57)

**Objetivo:** Transformar o chat do Desk em uma interface estilo WhatsApp com suporte real a todas as formas de mídia.

#### Bugs encontrados e corrigidos nesta wave

**BUG CRÍTICO — Mensagens do AI invisíveis no Desk**  
- **Causa raiz 1:** `calendar-agent.ts` → `sendAndSave()` fazia INSERT em `messages` sem o campo `client_id`.  
- **Causa raiz 2:** `GET /api/desk/conversations/[id]/route.ts` filtrava mensagens com `.eq('client_id', X)`, ignorando silenciosamente todas as linhas sem `client_id`.  
- **Efeito no usuário:** O bot respondia no WhatsApp mas a resposta nunca aparecia no Desk.  
- **Fix 1** (`calendar-agent.ts`): adicionou `client_id: conversation.client_id` ao INSERT.  
- **Fix 2** (`route.ts`): substituiu `.eq('client_id', X)` por `.or('client_id.eq.X,client_id.is.null')` para incluir linhas legadas.

**BUG — Áudio inbound não era armazenado**  
- **Causa:** `normalize-evolution.ts` não capturava `mediaUrl` de mensagens de áudio. Pipeline não incluía `'audio'` na condição de upload.  
- **Fix:** Capturar `audioMessage.url` no normalizador; adicionar `'audio'` ao `if (contentType === 'image' | 'audio' | ...)` no pipeline.

**BUG — `content_type` sempre `'image'` ou `'document'` no envio outbound**  
- **Causa:** `send-media/route.ts` tinha lógica hardcoded que forçava qualquer coisa que não fosse imagem a virar `'document'`, incluindo áudio e vídeo.  
- **Fix:** Ler `mediatype` diretamente do body da requisição e passá-lo sem transformação.

### 3.2 Wave 2 — `443e31a` (22:22)

**Objetivo:** Transcrição de áudio via Whisper, ticks de entrega de mensagens estilo WhatsApp, e atualização de mídia em tempo real sem re-fetch.

#### Bugs encontrados e corrigidos nesta wave

**BUG — Realtime: bolha de áudio/imagem mostrava "indisponível" por ~4 segundos**  
- **Causa:** O evento `INSERT` do Supabase Realtime dispara imediatamente quando a linha é criada, mas o campo `media_url` só é preenchido após o pipeline fazer o upload para o Storage (que pode demorar alguns segundos). O front renderizava a bolha incompleta.  
- **Fix:** Adicionado handler para evento `UPDATE` no canal Realtime do chat. Quando uma linha de mensagem é atualizada (ex.: `media_url` setado pelo pipeline), o front faz merge dos novos campos no estado existente sem refetch.

**BUG — Delivery ticks impossíveis: `evolution_message_id` não era salvo**  
- **Causa:** `sendTextMessage` e `sendMediaMessage` em `evolution.ts` tinham return type `Promise<void>`. Sem o ID de retorno da Evolution, era impossível fazer match quando chegava o evento `messages.update`.  
- **Fix A** (`evolution.ts`): todas as funções de envio agora retornam `Promise<string | null>` (o `key.id` da resposta da Evolution).  
- **Fix B** (`message/route.ts`, `send-media/route.ts`): salvam `evolution_message_id` no INSERT da mensagem.

## 13. Fragilidades, Riscos e Erros Ocorridos

### 13.1 Erros de Build em Produção (2 ciclos)

**Causa raiz:** A migration 032 adicionou 3 campos JSONB a `PanelBotConfig`. O tipo `PanelBotConfigInsert` herda via `Omit<PanelBotConfig, ...>`, tornando esses campos **obrigatórios** — mas o POST handler de `bot-config/route.ts` não os inclui.

**Attempt 1 (`4b39917`) — FALHOU:**
```typescript
// Tentativa: adicionar `& { field?: T }` sem omitir do base type
// Resultado: intersection com required não funciona em TypeScript
export type PanelBotConfigInsert = Omit<PanelBotConfig, 'id' | 'created_at' | 'updated_at'> & {
  lead_followup_steps?: FollowupStepConfig[] | null  // ← required ainda vence
  ...
}
```

**Fix definitivo (`419b8b0`):**
```typescript
// Correto: omitir do base type PRIMEIRO, depois redefinir como opcionais
export type PanelBotConfigInsert = Omit<
  PanelBotConfig,
  'id' | 'created_at' | 'updated_at' |
  'lead_followup_steps' | 'atendimento_followup_steps' | 'agendado_followup_steps'
> & { ... }
```

**Lição:** Qualquer novo campo `required` adicionado a `PanelBotConfig` precisa ser explicitamente omitido em `PanelBotConfigInsert` se o route de criação não o inclui — o campo precisa entrar no Omit, não apenas no `& {}`.

### 13.2 Circuit Breaker In-Memory

O `FollowupCircuitBreaker` é instanciado por ciclo de cron. Falhas entre ciclos distintos não acumulam — cada execução de cron começa com contador zerado. Isso é intencional (evita bloqueio permanente), mas significa que o threshold=3 só conta falhas **consecutivas no mesmo ciclo**.

### 13.3 Queries Sem `.limit()` (risco de performance)

As 6 queries sem `.limit()` foram corrigidas, mas identificamos o padrão de risco: toda query em `panel_bot_config`, `conversations`, `followup_cadence_steps` e `messages` que não filtra por `id` específico deve ter `.limit()` explícito. Revisão periódica recomendada.

### 13.4 Migrações em Produção

> ✅ Todas as migrações 029–035 foram confirmadas como aplicadas em 12/04/2026. Ver seção 17 para status completo.

### 13.5 Fallback de Templates

Se o banco tiver `lead_followup_steps = null` (antes da migration 032 ser aplicada), o sistema usa os defaults hardcoded. Isso é seguro — mas se alguém configurar os steps pela UI **antes** de aplicar a migration, a UI vai tentar salvar no campo JSONB que não existe ainda, gerando um erro silencioso do Supabase (coluna inexistente ignorada no upsert). **Aplicar a migration antes de disponibilizar a UI para usuários.**

### 13.6 Idempotency de `sendFollowupMessage()`

A chave de idempotência é `(conversation_id, cadence_type, step_key)`. Se o bot enviar com sucesso mas o INSERT em `messages` falhar, na próxima execução do cron o step já está marcado como enviado — a mensagem não será reenviada. O contato não vai receber duplicata, mas a mensagem pode não aparecer no Desk.

## 18. Fragilidades e Riscos Adicionais (Sessão 12/04 tarde)


### 18.1 RLS e Rate Limiting — Status Atual

**RLS:** Migration 036 implementou RLS em 11 tabelas core, incluindo propagation de client_id. O risco de exposição cross-tenant foi mitigado, mas recomenda-se validação forte em produção: testar cenários admin vs operador, client_id null legado, rotas service_role, realtime, follow-up/cron.

**Rate Limiting:** Implementado in-memory, integrado em 8 rotas, com calibração por tipo. O risco de DoS foi mitigado, mas recomenda-se monitorar falsos positivos, calibrar limites e planejar evolução para Redis/Upstash conforme escala.

### 18.3 Heurísticas de suggestedNextStep

`buildSuggestedNextStep()` usa lógica determinística simples (if/else chain). Funciona para casos básicos mas não captura nuances de conversas complexas.

**Preparação para LLM:** A função já retorna uma interface limpa (`{ action, label, priority }`) que pode ser substituída por chamada ao AI sem impacto na UI.

### 18.4 SLA Thresholds Hardcoded

Os thresholds de SLA estão hardcoded em `conduction.ts` (15min/60min) e `conversation-list.tsx` (30min/60min/120min). Não são configuráveis por tenant.

**Risco:** Clientes com SLAs diferentes não podem personalizar.  
**Recomendação futura:** Mover thresholds para `panel_bot_config` ou tabela dedicada.
