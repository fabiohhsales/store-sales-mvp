# Handoff — Áudio Inbound no Desk (2026-04-19)

## Contexto geral

O Desk é o painel de atendimento humano (`/desk`). Operadores visualizam conversas do WhatsApp em tempo real e podem assumir o atendimento do bot. Mensagens inbound de áudio chegam via Evolution API como OGG/Opus e precisam de dois fluxos independentes:

1. **Playback** — operador ouve o áudio no browser via `<audio>`
2. **Transcrição** — o pipeline converte o áudio em texto para o bot poder responder

Esses dois fluxos são **completamente independentes**: playback usa Supabase Storage; transcrição usa ffmpeg → OpenAI Speech-to-Text (`gpt-4o-mini-transcribe` por padrão).

## Problemas resolvidos nesta sessão

### 1. Buffer vazio passava pelos guards (media-storage.ts)

**Sintoma:** Áudio não tocava — player aparecia mas silencioso.

**Causa:** `Buffer.from(parsed.base64, 'base64')` retorna um Buffer de 0 bytes quando o base64 está inválido/corrompido, sem lançar erro. Em JS, `!Buffer.alloc(0) === false` — Buffer vazio é truthy. O guard `if (!recovered.buffer)` não disparava.

**Fix:** `src/lib/bot/media-storage.ts`
- Função `sanitizeBase64()` rejeita strings com charset inválido ou comprimento < 4
- Guard explícito `buffer.byteLength === 0` após `Buffer.from(...)` — se o buffer for vazio, `continue` para o próximo candidate em vez de retornar lixo

**Fix:** `src/app/api/desk/media/route.ts`
- Guard: `if (!recovered.buffer || recovered.buffer.length === 0)` → 404 com log `media_recovered_empty`

### 2. Deploy quebrado: `npm: command not found`

**Sintoma:** Build no EasyPanel falhava com `npm: command not found` após adicionar ffmpeg ao nixpacks.toml.

**Causa:** Usou `nixPkgs = ["ffmpeg"]` no nixpacks.toml. O Nixpacks usa um ambiente Nix para detectar e prover Node.js automaticamente. Ao declarar `nixPkgs`, o nixpacks **substitui** o ambiente Nix inteiro pelo declarado — e Node.js some.

**Fix:** `nixpacks.toml`
```toml
# ERRADO — substitui o ambiente Nix, Node.js some:
[phases.setup]
nixPkgs = ["ffmpeg"]

# CERTO — instala via apt no layer Ubuntu, não toca no Nix:
[phases.setup]
aptPkgs = ["ffmpeg"]
```

**Regra de ouro:** No nixpacks do EasyPanel, usar sempre `aptPkgs` para dependências de sistema. Nunca `nixPkgs` — isso vai contra a auto-detecção do nixpacks.

### 3. Player sumia após falha de transcrição (chat-view.tsx)

**Sintoma:** Áudio tocava normalmente, mas segundos depois o player sumia e aparecia o botão "Recarregar áudio" / badge "Falhou".

**Causa:** O `useEffect` em `MessageBubble` tinha `message.media_url` e `message.media_mime_type` no array de dependências. Quando a transcrição falhava, o pipeline atualizava esses campos no banco. O Realtime do Supabase disparava. O `useEffect` reexecutava, chamava `setMediaBust(Date.now())` que forçava um novo carregamento do áudio. Esse novo carregamento falhava por algum motivo → `mediaFailed = true` → player some.

Para mensagens inbound com `evolution_message_id`, o `baseMediaSrc` **nunca muda** quando esses campos são atualizados — a URL sempre usa `?msg_id=...`. Então as dependências eram desnecessárias e destrutivas.

**Fix:** `src/components/desk/chat-view.tsx` linha 333
```typescript
// ANTES:
}, [baseMediaSrc, message.id, message.media_mime_type, message.media_url])

// DEPOIS:
}, [baseMediaSrc, message.id])
```

**Princípio:** O reset do player só deve acontecer quando a **fonte da mídia muda**, não quando metadados de processamento são atualizados.

### 4. ffmpeg falha com exit 187 no Docker do EasyPanel

**Sintoma:** `[audio-conversion] ffmpeg_nonzero_exit { code: 187 }` — ffmpeg instalado mas não funciona.

**Causa:** Exit code 187 = sinal 59 (SIGSYS = "bad system call"). O Docker do EasyPanel usa seccomp padrão que bloqueia syscalls mais novas como `clone3`, usadas pelo binário ffmpeg do apt. O processo é lançado mas o kernel mata imediatamente quando tenta usar uma syscall bloqueada.

**Fix:** `ffmpeg-static` npm package + atualização do `nixpacks.toml`

O `ffmpeg-static` distribui um binário estático pré-compilado para Linux que não depende de glibc e não usa syscalls problemáticas.

```typescript
// src/lib/media/audio-conversion.ts
import ffmpegStatic from 'ffmpeg-static'

// no spawn:
proc = spawn(ffmpegStatic ?? 'ffmpeg', [...args], { stdio: 'pipe' })
```

```toml
# nixpacks.toml — aptPkgs removido, não é mais necessário
[phases.install]
cmds = ["npm ci --prefer-offline --no-audit --progress=false"]
```

### 5. OGG/Opus cru do WhatsApp não é um contrato confiável para transcrição

**Sintoma:** OGG/Opus cru do WhatsApp falhava na transcrição mesmo após tentativas com MIME alternativo e fallback entre providers.

**Causa:** O WhatsApp envia OGG com codec Opus em um formato que browsers e ffmpeg conseguem ler, mas não deve ser tratado como input confiável para APIs de speech-to-text. A documentação oficial da OpenAI para transcrição lista `mp3`, `mp4`, `mpeg`, `mpga`, `m4a`, `wav` e `webm` como formatos suportados, então o fluxo robusto é converter antes.

**Fix:** Padronizar a transcrição inbound em OpenAI + WAV:
- sempre converter OGG/Opus para WAV 16kHz mono com `ffmpeg-static`;
- enviar o WAV para `gpt-4o-mini-transcribe` por padrão;
- permitir override por `OPENAI_TRANSCRIPTION_MODEL`;
- remover o fallback de transcrição por Groq e as tentativas com OGG cru.

**Regra atual:** não confiar em OGG/Opus cru como formato de transcrição. O único caminho suportado pelo sistema é `OGG/Opus inbound -> WAV -> OpenAI`.

## Problemas recorrentes / armadilhas

### Buffer vazio é truthy em JS
```javascript
!Buffer.alloc(0) // false — Buffer vazio não é falsy!
Boolean(Buffer.alloc(0)) // true
```
Sempre usar `buffer.length === 0` ou `buffer.byteLength === 0` como guard explícito.

### nixpacks: `nixPkgs` vs `aptPkgs`
- `nixPkgs`: substitui o ambiente Nix inteiro → Node.js e npm somem → build quebra
- `aptPkgs`: instala via apt no layer Ubuntu → Node.js não é afetado
- **Regra:** Para qualquer dep de sistema no EasyPanel, usar sempre `aptPkgs`

### Realtime + useEffect: cuidado com deps que mudam por efeito colateral
O pipeline atualiza vários campos do banco depois de processar uma mensagem (`processing_status`, `derived_text`, `media_url`, `media_mime_type`). Esses updates disparam o Realtime, que atualiza o estado React. Qualquer `useEffect` que tenha esses campos no array de deps vai reexecutar desnecessariamente e pode causar side effects (como forçar reload de mídia).

**Padrão seguro:** Só incluir no dep array aquilo que muda a **intenção** do efeito, não metadados de processamento.

### OGG/Opus do WhatsApp não deve ser enviado raw para transcrição
O áudio inbound do WhatsApp deve ser convertido para WAV antes da transcrição. O sistema não usa mais Groq nem tentativas com OGG cru como fallback. Sem `ffmpeg-static` funcional ou sem `OPENAI_API_KEY`, não há transcrição.

### ffmpeg em Docker
Binários apt de ffmpeg usam syscalls que podem ser bloqueadas por seccomp. A solução confiável é `ffmpeg-static` (npm) — binário estático que funciona em qualquer container sem configuração adicional.

## Pendências em aberto

### Áudio some após refresh da página (investigar)
**Sintoma relatado:** Áudio toca com a página aberta mas após refresh não aparece.

**Hipótese mais provável:** A conversa tem `hasMore=true` (50+ mensagens). Ao recarregar, a API retorna as 50 mais recentes. Se o áudio estiver além dessas 50 (mensagem mais antiga), o bubble não renderiza. O arquivo em si está íntegro no Supabase Storage — foi confirmado `audio_stored_inline { bytes: 10170 }`.

**Para investigar:** Após refresh, verificar nos logs se aparece `audio_stored_inline` (arquivo servido normalmente) ou `storage_missing_for_msg_id` (bug real). Verificar também se o usuário precisa rolar para cima para encontrar a mensagem.

**Se for paginação:** O fix seria scroll infinito / lazy load de mensagens mais antigas no chat do Desk.

### Qualidade de transcrição (melhoria futura)
Atualmente o WAV é gerado a 16kHz mono, que é o ideal para Whisper. Nenhuma ação necessária.

### OPENAI_API_KEY é obrigatória para transcrição
O chat principal ainda pode operar com OpenAI ou Groq, mas a transcrição inbound agora depende explicitamente de `OPENAI_API_KEY`. Se só `GROQ_API_KEY` estiver configurada, o playback continua funcionando e a mensagem entra em handoff seguro, mas não há transcrição automática.
